## F1 翻译记录增强

**现状**：`options.html:495` 只有「清空翻译记录」一个按钮。

**要加**：
- 点某条记录 → 复制它的译文
- 一行「重翻」→ 用当前配置重发这条原文
- 搜索框（按原文 / 译文 / 配置名过滤）

**为什么好做**：数据早就在存档里了（`src / dst / configName / lang / ts`），
`lib/store.js` 的 `appendHistory` 已经在写。这是**纯 UI 活**，不碰请求引擎。

**注意截断上有两个不同的数，别搞混**：

- `settings.maxChars`（默认 8000）= **发给接口的原文上限**，截断在 `background.js:476`（请求前）
- 历史记录自己的截断是**写死**的：`lib/store.js:434-435` 原文 2000 / 译文 5000
- `settings.historyMax`（默认 10）= **保留条数**，0 = 不记

所以 F1 的 UI **只管读，不要再截一次** —— 存档里存的已经是截过的。

**工作量**：半天以内。风险低（只动设置页）。

## F2 导入时勾选条目

**现状**：`lib/store.js` 的 `importState()` 是**整体替换** —— 导入一份文件就把当前配置全换掉。

**要改成**：导入前先列出文件里有哪些配置，逐条勾选要导入的，再说怎么合并
（覆盖同 id / 全部新建 / 全部替换）。

**为什么值得做**：和「分享版导出」（去 Key 的导出）凑成分享生态的两半 ——
现在导出方便，导入却很粗暴，收到别人的配置只能整体替换自己的。

**工作量**：1 天左右（要改 `importState` 的签名 + 设置页弹层 + 断言）。风险中低。

## ~~F3 第二级轮换：配置健康检查~~（已丢弃 2026-11-10）

**现状**：第一级「换 model 重试」和后备请求链（`config.fallbacks[]`）都已落地。
第二级「后台探测哪条配置活着、主配置挂了自动切」**没有**（`grep health/probe` 全仓 0 处）。

**真正要决策的是这个**（技术不难，难在行为定义）：

1. **探测频率**：多久探一次？探一次就是一次真实请求（花额度）。
2. **探测内容**：发一句固定短文本？还是只用上次失败的事实？
3. **切换时机**：连续失败 N 次才切？还是探测失败立刻切？
4. **切回来吗**：主配置恢复了要不要自动切回？如果不切回，用户以为配置坏了。
5. **用户可见性**：切换要让用户知道吗？（「不做隐式行为」是项目原则）

**我的看法**：这条的收益不如「把失败提示做得更清楚」。现在请求挂了面板上就有
`HTTP xxx` 和错误原因，用户自己就知道该换哪条。**「配一次就不用管」听着美好，
但后台静默探测会持续消耗用户额度、还可能让「当前用的是哪条」变得不可预测。**

**建议**：先不做，或只做「明确报错 + 一键切到下一条」这种**可见的**半自动。

## ~~F4 done 归档 requestId~~（已丢弃 2026-11-10）

**问题**：切配置的那一瞬间，旧配置的结果可能被当成新配置的缓存显示出来。**毫秒级窗口**。

**要改**：后台回包带 `requestId`，前端按 id 归档。碰的是请求引擎 + 缓存 + 流式三处。

**我的看法**：**收益极小**。毫秒级竞态窗口 + 用户得先手快去切配置才能撞上。
ROADMAP 原文自己写着「改动大收益小」。**建议永久搁置**，除非真有人报这个 bug。

## F5 本地 OCR（Tesseract.js）

**现状**：OCR 全是走外置接口（硅基流动 / 百度 / 商汤 / 蚂蚁百灵等，你在用的就是这些）。

**要做的代价**：
- 引擎 4.7 MB + 中英语言包 → 包从 **119 KB 涨到约 5.8 MB**（50 倍）
- Tesseract.js 有 WASM，要跟着打包（零构建原则不破，但包体量变了）
- 识别质量明显低于云端模型，尤其截图里的小字

**关键判断**：**和现在 119 KB 的定位是两种产品**。而且这版已经内置 bilibili 多模态翻译
（**图片直传不需要先 OCR**）—— 用户没配 OCR 也能翻图。

**除非**你要的是「完全离线、不发一个字节出去」，否则这条的收益已经不太成立。
等明确需求信号再动。
