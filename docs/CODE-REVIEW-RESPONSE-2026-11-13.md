## 一、P0-1 OCR 自建供应商被复制 —— 我上一轮引入的

### 现状

上一轮修「顺序被重置」时，新的 pushOne 循环和旧的补推循环**同时留着**：

```js
for (const p of saved) pushOne(p);        // 新增：把 saved 全放好
for (const d of OCR_PROVIDERS) pushOne(d);
for (const p of saved) { if (!builtin) providers.push(...) }   // 旧的：又推一遍
```

第三段没有 placed 检查。实测：

```
第1轮: [my-own, 3×内置, my-own]
第2轮: [my-own, 3×内置, my-own, my-own]
第3轮: [... 再 +1]
```

每过一次 loadState 就多一条，**已进 1.3.2 包**。

### 为什么测试全绿

那条断言写的是「自建的最后一条是 my-own」——**恰好锁住了这个 bug**。
它不是「没测到」，是「测错了方向」。已改成「只出现一次 + 保持存档里的先后」。

### 教训

我上一轮加断言时，是从**当时的实现**反推期望值，而不是从**需求**出发。
实现有 bug，断言就跟着把 bug 固化下来 —— 这比没断言更糟，因为它给人「已验证」的安全感。

### P1-2 图片多槽兜底仍会撞

### P1-3 done 判废窗口

```js
if (!alive()) return;
if (result && result.text) { await appendHistory(...) }   ← await
runCtrls.delete(cid);
safePost({ type: "done", ... });                          ← 无再判
```

两处都补：`appendHistory` 之后再加一道 `alive()`；
delete 前校验 `runCtrls.get(cid) === ctrl`（同 cid 可能已被新批次重建）。

## 八、关于「数字必须同一时点」

第八版指出我贴的「557/0 连跑两遍」出自 19:30 的日志，而 21:16 的日志是 556/1。
这是真的：我在同一轮里边改代码边引用先前跑出来的数字。

**已落地**：`npm test` 现在末尾打一行带时间戳的汇总，各测试脚本把通过数写进
`.test-counts.json`，汇总脚本读它并打印：

```
========================================================
全量汇总  2026-11-14 23:07:50
  test-lib 1088 ｜ test-engine 89 ｜ test-strip 19 ｜ e2e-ui 557
  合计 1753 项
========================================================
```

以后回应里的数字直接抄这一行，时间戳跟着走，不会再出现「引用 19:30 的数字说 21:16 的事」。
